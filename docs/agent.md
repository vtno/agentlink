# Agent

`AgentLink.Relay.Agent` opens one agent through `AgentLink.Agent`. `AgentLink.Agent.Process` is the production behaviour. It runs the `command` and `args` from `AgentLink.Agent.Launch`. The default suite sets `:agent_link, :agent_module` to a fake. `test/lifecycle_test.exs` and `test/release_lifecycle_test.exs` set `AgentLink.Agent.Process` and start `test/fixtures/agentlink_hold_fixture.py`. Stdout still arrives as `{ref, {:data, binary}}`.

`AgentLink.Agent` is that behaviour. `open/3` takes the owner, an `AgentLink.Agent.Launch`, and the workspace. `write/2` and `close/1` stay as they are. A link's `program` is metadata. `opencode` is one example. `program` does not choose the module, the command, or the args. When `program` is missing, `AgentLink.Link` uses `opencode`.

Each `init/1` creates the workspace, then calls `AgentLink.Agent.Launch.load/1` once. That call returns the `AgentLink.Link` and the `AgentLink.Agent.Launch` from the same read. The relay passes that link to `AgentLink.Uplink` as `:link`. The uplink's `init/1` does not read the file again. A watch, a non-parking close, and an uplink started without `:link` call `AgentLink.Link.read/1`. `command` and `args` are not fields of `AgentLink.Link`. Changing only those fields does not redial and does not replace the running process. The next `init/1`, including a supervisor restart, calls `load/1` again. The launch is not stored in the supervisor child arguments.

`AgentLink.Agent.Process.open/3` is the behaviour callback. The relay calls it. The caller must be `owner`. A bare name is resolved by the finder. `open/4` accepts that finder and is not a callback. The finder `open/3` uses is `&System.find_executable/1`. A path that is absolute on this host is used unchanged. On Unix that path starts with `/`. On Windows it starts with two slashes, or with a drive letter, a colon, and a slash. Each of those two slashes may be `/` or `\`. The slash after the colon may be `/` or `\`. On Windows, a single leading slash is not absolute. Any other command is rejected before `File.stat/1`. `File.stat/1` must report a regular file. `File.stat/1` follows symlinks. `open/3` then calls `Port.open/2` with `{:spawn_executable, path}`, `:binary`, `:exit_status`, `:use_stdio`, `{:args, args}`, and `{:cd, cwd}`. `:env` is omitted, so the port inherits the VM environment. `:stderr_to_stdout` is omitted, so stderr is not merged into `{port, {:data, binary}}`. On Linux the VM's port spawn makes the command a session leader, and that pid is the process group leader. On Linux, `close/1` reads `/proc` and records the start time of that pid and of each descendant, including a descendant that called `setsid`. It signals `SIGTERM` only when that start time still matches. A group leader is signaled with the negative pid. A descendant whose process group is not that pid is signaled by its own pid. `close/1` then closes the port, which closes the child's stdin, and waits up to `:agent_stop_timeout` milliseconds. The default is `5000`. When a recorded start time still matches, `close/1` signals `SIGKILL` the same way and waits again. The second wait is `:agent_stop_timeout`, or `1000` milliseconds when that value is shorter, so a timeout of `0` still observes the reap. `close/1` returns `:ok` only when every recorded process is gone. It returns `{:error, :timeout}` when one remains, and `{:error, :no_kill}` when `kill` is not on `PATH`. On macOS, `close/1` closes stdin and does not signal a process group, does not walk descendants, and does not create a Job Object. On Windows, `close/1` closes stdin and does not signal a process group and does not create a Job Object. `write/2` returns `:ok` when the port is open and `:closed` otherwise. `AgentLink.Release.forward_signals/1` wraps each Burrito binary `mix.exs` ships and compiles the wrapper with `zig cc`. The Linux target is `x86_64-linux-gnu` and the macOS target is `aarch64-macos`. Those wrappers put the Burrito process in its own process group, forward one `SIGTERM` or one `SIGINT` to that process's direct child, which is the VM, when its recorded start time still matches. A grandchild such as `erl_child_setup` is not the target. The wrapper waits until the VM is gone and exits with the VM's status. The Windows target is `x86_64-windows-gnu`. That wrapper runs the Burrito process in a Job Object with `KILL_ON_JOB_CLOSE`, turns Ctrl-C, Ctrl-Break, and console close into one Ctrl-Break for the child process group, waits, and exits with that process's status.

For `session/new` and `session/load`, the relay fills a missing, null, or empty `cwd` in params with its workspace, `AgentLink.Paths.workdir()`, before the message reaches the agent. An explicit `cwd` passes through unchanged.
